## Copy-paste for the Web teammate

> Integrate the four M7 migration files in timestamp order. Use the exact hosted definitions and installed NW11 history for rehearsal. Where a migration rejects a differing installed function body, reconcile against the newer definition and rerun the SQL and Web workflow tests. Coordinate the Web cutover with the operational visibility migration because raw Planning reads will stop returning drafts.
>
> Subtask create/edit still uses R7/NW commands. Add `p_payload.start` as a date-only string. Include it in the same request body when previewing, confirming, retrying, or looking up a receipt. Use `root.scheduling.today` for the create default and the returned `start_date`, `started_at` and `effective_status` on the work tree. Existing records may have no planned date or activation timestamp. For an overdue parent, ask for a valid historical schedule within its bounds or use the authorized parent schedule editor first. The start action remains `transition_task_status(..., 'in_progress', ...)` for the actual assigned Task Lead. Use the backend projection for descendant activation. Confirm that the scheduled activation job runs on the deployment database.
>
> Use `m7_work_proposals(p_root, p_node)` for the Lead-review card and capability flags. Send proposed progress or completion through `m7_propose_work(p_root, p_node, p_request, p_kind, p_terms, p_supersedes)`. `p_kind` is `progress` or `completion`. Terms contain `note`, optional integer `progress` from 0 to 99, optional `blocker`, and optional `attachments`. The Task contributor progress form requires the percentage. For returned work, create a fresh request ID and put the returned proposal ID in `p_supersedes`. Decide with `m7_decide_work(p_proposal, p_request, p_approve, p_note)`. A return requires a note. Repeat exactly the same request and UUID to verify an uncertain outcome. Refresh work and review facts after a confirmed receipt. The current eligible reviewer is recalculated before decision, and approval refuses a stale baseline. A contributor's accepted completion submission records accepted work and does not substitute for the Subtask Lead's final submission or the Task's independent final review. Keep those actions separate.
>
> Attach proposal files to the private `m7-work-evidence` bucket at `<author>/<root>/<node-or-root>/<request>/<safe-filename>`. Persist upload progress against the request UUID. Send `fileName`, `filePath`, `fileSize`, and `mimeType`. Use the existing approved MIME list and a 25 MiB file limit. Use signed URLs from that bucket for authorized review. The pending and accepted evidence remains attached to the original proposal. Preserve that author in Web history and identify the Lead separately as the actor who applied the change. Keep existing direct-completion evidence and independent final Task evidence on their current paths.
>
> Only the assigned Task Lead who is also the Subtask Lead uses direct `complete_subitem` for ordinary Office project work. A different Subtask Lead sends a completion proposal to the Task Lead. Use `entity_type = 'm7_work_proposal'` plus `task_id` and `work_node_id` to open Lead review at the exact work location. Use `entity_type = 'm7_personal_work_proposal'` plus `project_id`, `task_id`, and `work_node_id` to open a Personal branch. Keep both notice types separate from the existing final Task review screen.
>
> Use `m7_office_assignments(p_workspace)` for Office assignment discovery. It returns `key` and `workspace_id` for authorized, actually appointed work. Continue to use the operational workspace and work-tree reads for displayed details. For authorized Web draft management, use `m7_draft_projects()`, `m7_draft_project(p_project)`, and `m7_draft_task_create(p_project,p_group,p_title)`. The draft detail returns the funding flow, groups, and tasks. Call `m7_draft_work(p_project,p_root,p_operation,p_revision,p_request,p_command,p_payload,p_fingerprint)` with `tree`, `impact`, `command`, `patch_task`, or `allocate_task`. The parameters after `p_operation` are optional according to the selected operation. For impact-checked edits, send the matching `p_fingerprint` and exact `p_payload`. For draft allocation, send the request UUID and `p_payload` with `lines` and `reason`. Review other draft-dependent Web screens and adjacent draft administration APIs before deploying the visibility migration.
>
> Use `m7_work_allocation_context(p_task,p_node)` for scoped account choices and current capability. In project funding views, use `canAllocateTask` for allocation and retain existing authorization and return capabilities separately. Save Task allocations with `allocate_project_task_funding(p_task,p_lines,p_reason,p_key)`, passing `p_lines` as an array of `{sourceId, amount}` objects. Reuse the exact key and terms on retry. Preserve Head authorization, Accounting release, acknowledgement, liquidation, settlement, return and closeout controls.
